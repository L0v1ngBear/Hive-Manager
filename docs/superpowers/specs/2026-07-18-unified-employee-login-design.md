# Hive 网页端与小程序统一员工登录设计

## 1. 状态

- 设计日期：2026-07-18
- 设计状态：已由用户确认
- 适用范围：管理网页端、小程序、统一认证后端、员工账号数据与登录相关说明文档

## 2. 背景与问题

Hive 当前已经使用同一张 `user` 表承载网页端和小程序账号，但登录行为存在不一致：

- 小程序微信手机号登录只允许匹配已有企业员工；没有匹配时后端直接拒绝。
- 小程序前端仍保留“已登录但未加入组织”的状态分支。
- 历史迁移和用户手册仍描述“微信登录先创建无企业账号”，与当前后端行为矛盾。
- 网页端员工创建会生成工号和默认密码，但创建结果没有清晰交付首次登录凭证。
- 网页端登录框提示“员工编号或邮箱”，而后端实际支持登录账号、工号或手机号，不支持邮箱登录。
- 同一手机号匹配多个企业时，小程序要求用户改用账号密码，没有提供自然的企业选择流程。

这些差异导致用户无法明确判断账号应由谁创建、手机号如何生效，以及网页端和小程序是否属于同一账号体系。

## 3. 目标

1. 网页端和小程序统一使用企业员工账号，不再创建可登录的无企业微信临时账号。
2. 网页端员工档案是账号身份的唯一数据源，管理员控制员工手机号、岗位、角色和状态。
3. 网页端支持登录账号、工号或手机号加密码登录，并提供短信首次激活与密码重置。
4. 小程序支持微信手机号快速匹配员工；多企业时由用户明确选择企业。
5. 未建档人员只能通过管理员生成的短期组织邀请码加入，不能凭微信手机号自动成为正式员工。
6. 所有客户可见错误由后端返回稳定业务原因码和中文提示；前端不依赖提示文字判断流程。
7. 停用、离职和企业不可用状态在网页端与小程序保持一致，并且不会触发重复登录跳转。

## 4. 非目标

- 不引入独立的微信用户中心或消费者账号体系。
- 不允许匿名用户仅凭手机号自动创建正式企业员工。
- 不在本次设计中改变员工业务权限模型、审批模型或许可证计费规则。
- 不把邮箱加入登录标识；未来若需要邮箱登录，应单独设计邮箱验证与唯一性规则。

## 5. 统一身份模型

### 5.1 员工账号

- `user` 与员工扩展档案共同构成一个企业员工账号。
- 企业内手机号必填，并以规范化后的 `phone_hash` 用于查重和登录匹配。
- `login_name` 默认使用系统生成的工号；企业负责人等已有自定义登录账号继续兼容。
- 同一企业内 `login_name` 唯一，`phone_hash` 也必须唯一。
- 同一自然人可以在不同企业存在员工账号，因此手机号允许跨企业重复。

### 5.2 账号可用性

正式登录必须同时满足：

- 员工记录存在且已归属企业；
- 员工状态允许登录；
- 企业处于可用状态并在当前部署允许范围内；
- 企业许可证和用户额度策略允许该账号使用；
- 账号认证版本有效。

网页端和小程序调用同一套可用性校验，避免渠道间状态不一致。

## 6. 网页端登录流程

### 6.1 员工建档

管理员在员工管理页创建员工，至少填写姓名、手机号、部门、职位、角色和员工状态。系统执行：

1. 规范化手机号并计算不可逆哈希。
2. 校验同一企业内手机号唯一。
3. 生成工号，并将工号作为默认 `login_name`。
4. 创建员工档案、角色关系和认证信息。
5. 返回员工工号和“等待首次激活”状态，不返回企业共享默认密码。

### 6.2 首次激活与忘记密码

网页登录页统一提供“首次登录 / 忘记密码”入口：

1. 用户输入绑定手机号；手机号对应多个企业账号时，可补充工号或登录账号定位。
2. 后端发送短信验证码并进行频率限制。
3. 用户验证验证码并设置密码。
4. 后端清除 `must_change_password`，递增认证版本，并使旧会话失效。

员工创建不再依赖所有人都知道的全局默认密码。历史账号仍可使用现有密码登录；被标记为必须修改密码的账号继续进入强制修改流程。

### 6.3 正常登录

- 登录输入框文案改为“工号、手机号或登录账号”。
- 后端继续支持 `login_name` 和手机号哈希查询。
- 多企业手机号若无法唯一定位，提示用户补充工号或登录账号，而不是随机选择账号。
- 登录成功后根据角色权限进入管理网页。

## 7. 小程序微信登录流程

### 7.1 初次手机号授权

小程序调用微信手机号授权能力，将一次性 `phoneCode` 发送到后端。后端换取手机号、计算哈希并查询所有允许企业内的员工账号。

### 7.2 查询结果为零

- 不创建正式账号，也不签发登录令牌。
- 返回业务原因 `EMPLOYEE_NOT_FOUND` 和中文提示“管理员尚未添加该手机号，请联系企业负责人或使用组织邀请码加入”。
- 小程序展示“重新授权手机号”和“使用组织邀请码加入”两个动作。

### 7.3 查询结果为一个

- 执行统一账号和企业可用性校验。
- 校验通过后签发正式令牌、响应加密密钥、权限和企业信息。
- 校验失败时返回对应业务原因和中文提示，停留在登录页。

### 7.4 查询结果为多个企业

多企业选择是正常流程，不使用异常提示代替交互：

1. 后端返回 `TENANT_SELECTION_REQUIRED`、企业简要列表和短期一次性 `selectionTicket`。
2. 小程序展示可用企业名称和标识。
3. 用户选择企业后，请求企业确认接口并提交 `selectionTicket` 与 `tenantCode`。
4. 后端验证凭证绑定的手机号哈希、候选企业、有效期和一次性状态，再签发正式登录令牌。

企业选择凭证不得包含明文手机号，有效期建议为五分钟，成功使用后立即失效。

## 8. 组织邀请码加入流程

只有具备员工创建权限的管理员可以生成短期组织邀请码。未建档用户可以：

1. 输入管理员提供的组织邀请码。
2. 填写姓名并完成手机号所有权验证。
3. 手机号验证可使用微信手机号授权产生的短期验证凭证，或使用短信验证码；两者满足其一即可。
4. 设置网页端登录密码。
5. 后端再次校验邀请码、企业可用性、用户额度和企业内手机号唯一性。
6. 创建普通员工账号和默认普通员工角色，岗位与更高权限由管理员后续维护。
7. 创建成功后签发正式登录令牌。

邀请码必须短期有效、一次或有限次数使用，并绑定生成企业。加入操作应记录审计日志。

## 9. API 契约

### 9.1 客户可见业务原因

认证响应增加稳定的 `reason` 字段，至少包含：

- `EMPLOYEE_NOT_FOUND`
- `TENANT_SELECTION_REQUIRED`
- `ACCOUNT_DISABLED`
- `EMPLOYEE_RESIGNED`
- `TENANT_UNAVAILABLE`
- `TENANT_LICENSE_UNAVAILABLE`
- `ACCOUNT_ACTIVATION_REQUIRED`
- `PHONE_ACCOUNT_AMBIGUOUS`
- `INVITATION_INVALID_OR_EXPIRED`

后端同时返回中文 `msg`。前端只能根据 `reason` 决定页面动作，不能匹配中英文消息文本。

### 9.2 微信登录响应

微信登录结果使用可判别结构：

- 已登录：`flowStatus=LOGGED_IN`，包含现有 `LoginVO` 信息。
- 需要选企业：`flowStatus=TENANT_SELECTION_REQUIRED`，包含 `selectionTicket` 和候选企业列表。
- 未建档及账号不可用：使用对应业务原因和中文提示，不签发令牌。

为减少上线风险，可以保留现有单企业成功响应字段，并在外层增加流程字段；小程序完成适配后再移除旧兼容分支。

## 10. 前端行为

### 10.1 网页端

- 登录框改为真实支持的登录标识文案。
- 增加清晰的首次激活入口，并复用短信验证和密码设置能力。
- 员工创建成功后展示工号、绑定手机号掩码和首次激活说明。
- 员工列表明确展示账号状态和手机号是否可用于小程序登录。

### 10.2 小程序

- 移除“微信登录成功但没有企业”的会话分支。
- 未建档时展示联系管理员和邀请码加入入口。
- 多企业时展示企业选择页或登录页内选择面板。
- 停用、离职等错误只提示一次，不清理后立即再次触发登录跳转。
- 保留账号密码登录作为辅助方式，其账号体系与网页端完全一致。

## 11. 数据约束与迁移

上线前执行只读审计：

1. 查找同一企业内重复 `phone_hash`。
2. 查找 `tenant_code IS NULL` 的历史微信临时账号。
3. 查找缺少员工扩展档案、角色或有效状态的账号。
4. 查找手机号哈希为空但仍需要登录的员工。

迁移规则：

- 重复账号不自动删除；生成清单，由明确规则合并后再建立唯一约束。
- 历史无企业账号若能与一个正式员工手机号匹配，则合并必要的微信订阅绑定并停用旧记录。
- 无法匹配的历史账号保留为不可登录待处理记录，不自动赋予企业或权限；以后通过有效邀请码加入时可安全复用。
- 清理完成后增加企业内手机号唯一约束 `UNIQUE (tenant_code, phone_hash)`。MySQL 对 `NULL` 的处理允许历史待处理记录暂存，但认证查询必须排除无企业账号。
- 保留现有企业内登录账号唯一约束。

数据库迁移必须先检查重复数据；发现冲突时停止，不提供绕过参数。

## 12. 安全与隐私

- 明文手机号不写入应用日志，数据库继续保存手机号掩码与不可逆哈希。
- 微信 `phoneCode`、短信验证码、企业选择凭证和手机号验证凭证均不得记录。
- 短信发送、验证码失败、微信登录和企业选择接口均设置账号、手机号哈希和 IP 维度限流。
- 企业选择凭证和手机号验证凭证必须短期、一次性，并绑定用途。
- 未验证手机号所有权前不返回该手机号关联的企业列表。
- 邀请加入创建的默认角色只能包含普通员工基础权限。

## 13. 错误处理

- 所有客户可见认证错误由后端返回中文。
- 前端根据业务 `reason` 决定提示、企业选择、激活或邀请加入流程。
- 401 仅用于登录令牌缺失或失效；员工未建档、停用和企业不可用使用明确的 403/409 业务状态，避免触发公共请求层的循环登录重定向。
- 日志可以保留内部技术信息，但不得输出手机号、验证码、令牌或响应加密密钥。

## 14. 测试方案

### 14.1 后端

- 网页端工号、手机号和自定义登录账号登录。
- 首次激活、验证码过期、错误次数限制和密码重置。
- 微信手机号零匹配、单企业匹配和多企业匹配。
- 企业选择凭证过期、篡改、跨手机号使用和重复使用。
- 员工停用、离职、企业不可用和许可证不可用。
- 邀请码有效、过期、错误企业、手机号重复和用户额度已满。
- 并发创建同手机号员工时唯一约束生效。
- 客户可见认证提示中文契约测试。

### 14.2 网页端

- 登录框文案和实际支持的标识一致。
- 员工建档手机号必填、格式校验和重复提示。
- 首次激活、忘记密码和强制修改密码完整流程。
- 创建成功后正确展示工号和激活说明。

### 14.3 小程序

- 未建档提示与邀请码入口。
- 单企业直接登录。
- 多企业选择后登录。
- 停用、离职和企业不可用只提示一次，不重复跳转。
- 账号密码登录与网页端使用相同账号。
- 邀请加入可使用微信手机号验证凭证或短信验证。

## 17. 验收标准

- 管理员创建员工后，该员工可使用同一手机号在网页端完成首次激活，并在小程序微信授权后登录。
- 未建档手机号不会自动获得正式账号或权限。
- 多企业手机号可选择企业并成功登录。
- 网页端和小程序对停用、离职和企业不可用返回一致结果。
- 登录失败不产生重复页面跳转。
- 同一企业无法创建重复手机号员工。
- 所有客户可见认证提示为中文，前端流程不依赖消息文本。
- 用户手册、代码注释、接口行为与本设计一致。
