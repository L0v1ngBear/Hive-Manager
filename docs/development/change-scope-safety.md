# Hive 变更影响范围控制规范

## 1. 目标

每次修改只解决已经明确的问题，不改变目标范围之外的既有功能、数据、接口、权限、样式和部署行为。

“不影响其他功能”不是仅确认当前页面可以使用，而是要保证共享依赖、上下游流程、旧数据兼容和发布产物均没有产生非预期变化。

## 2. 修改前

开始修改前必须记录或在工作说明中明确：

- 目标：本次需要修复或新增的具体行为。
- 非目标：本次明确不调整的页面、模块、接口和业务规则。
- 兼容边界：线上已有数据、旧字段、旧接口、权限角色、缓存和部署配置是否需要继续兼容。
- 验证范围：直接功能、相邻功能、共享契约和发布产物分别使用什么方式验证。

修改或删除任何函数、变量、样式、接口、权限码、字段或配置前，必须先完成全仓引用检索，并检查：

1. 模板、脚本、测试和构建产物是否仍引用该符号。
2. 同一文件内未展示的提交、导出、打印、详情和编辑流程是否依赖该符号。
3. 共享组件、公共工具和全局样式有哪些调用方或覆盖对象。
4. 后端接口、数据库、缓存、消息、审批和状态流转是否存在上下游依赖。
5. 线上旧数据或旧部署配置是否会经过本次修改路径。

仅凭“页面已经不展示”“搜索到的引用看起来是辅助代码”或“类型检查没有报错”不能作为删除依据。

## 3. 实施规则

- 使用能够修复根因的最小差异，不在同一次修改中顺手清理、重命名或重构无关代码。
- 页面级问题优先使用页面级样式和局部组件处理，不新增或扩大无边界的全局覆盖。
- 删除展示内容时，只删除展示及其专用代码；提交、保存、导出、打印、权限和数据转换所依赖的代码必须独立核对。
- 修改公共能力时保持现有调用方默认行为不变；新行为应通过显式参数、局部入口或兼容分支启用。
- 修改接口或数据结构时，除非需求明确允许破坏性升级，否则保留旧数据读取和旧字段兼容，并使新旧部署过渡可验证。
- 不得修改与目标无关的用户工作区文件，不得覆盖或清理已有未提交改动。
- 如果修复必须扩大到其他模块，应先说明原因、影响面和验证方案，获得确认后再继续。

## 4. 验证门槛

每次修改至少完成以下验证：

1. 增加或更新一个能复现原问题的回归测试，修复前失败、修复后通过。
2. 运行目标模块测试，覆盖正常路径、失败路径、权限路径和兼容路径。
3. 运行使用同一共享依赖的相邻模块或契约测试。
4. 前端修改运行 lint 和生产构建；后端修改运行相关测试及正式打包。
5. 检查完整测试结果，并明确区分本次新增失败和已有无关失败；不得隐瞒或将新增失败标记为无关。
6. 复查 `git diff --check`、变更文件清单和最终提交，确认没有无关改动。
7. 生成部署包时校验源码提交、文件数量、前端 manifest、后端 JAR、迁移数量及 SHA-256。

测试不能证明未覆盖的行为绝对安全。对于共享样式、权限、状态机、数据库迁移和公共工具等高影响修改，还必须进行调用方审计或必要的页面/API 冒烟验证。

## 5. 删除代码专项规则

删除前必须满足全部条件：

- 全仓引用已经检索，动态引用、模板引用和字符串映射也已检查。
- 被删除内容只服务于本次明确移除的功能。
- 保留下来的提交、保存、导出、打印、详情、权限和兼容流程不依赖它。
- 有测试能够在依赖被误删时失败，而不是只检查页面文字是否消失。
- 删除后的目标测试、相邻测试和生产构建均通过。

如果无法证明以上条件，保留代码并缩小修改范围。

## 6. 异常处理

出现以下情况时必须停止扩大修改并重新评估：

- 修改共享代码后出现其他页面或模块失败。
- 为通过测试需要删除测试、跳过测试或放宽核心断言。
- 发现线上数据与当前模型不一致。
- 发现需求会改变权限、状态流转、数据库或公共接口。
- 无法区分失败是本次引入还是既有问题。

重新评估后应先恢复到最小安全方案，再记录新增影响范围；不得带着未解释的跨模块影响进入发布包。
